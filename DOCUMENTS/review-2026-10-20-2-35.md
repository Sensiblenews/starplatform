- **이미 있음이 많다**: 07·21·23은 사실상 구현돼 있고, 01·03·05·08·15·22·25·28·29는 핵심이 있다. 재개발하지 않는다.

- **이번 검토에서 새로 나온 위험**: 11번의 DB 커넥션 풀 설정 주석 처리(대기 무제한). 장애 시 요청 정체와 경보 정지의 공통 원인이 될 수 있어 우선 처리 대상으로 제안한다(설정 파일 수정이라 승인 필요).

### 2-2. 단계별 제안 (견적 단위)

요청서의 "조치 20개"를 위험도와 기존 자산 기준으로 3개 묶음으로 나눴다. 각 묶음은 앞 묶음을 전제로 하며, 따로 견적·승인한다. 금액·일정은 범위 확정 후 별도 회신.

**1차 — 경보 상세 + 메일 딥링크 + 권장 조치 + 재확인** (규모: 중, 서버 상태를 바꾸는 조치 없음)

- 경보별 상세 페이지(신규 JSP 1개): 경보 ID 기준으로 발생·등급 변화·확인·메일 이력(기존 `WH_SYS_ALERT_EVENT` 재사용), 해당 항목의 최근 24시간 지표(기존 `SystemMetricsCollector` 링버퍼), 권장 조치 단계 표시
- 메일 링크를 상세 페이지로(`?alertId=`). 링크를 열면 기존 로그인+OTP 를 거친다. 메일에는 비밀정보·조치 실행 링크를 넣지 않는다
- "이 항목만 지금 재확인" 버튼(조회만, 상태기계 집계와 분리 — 3장 ⑦ 참조)
- 조치 메모·담당자 기록(30단계 22번 흡수): 이벤트 테이블에 `ACTION` 타입 추가 또는 컬럼 추가 → **DDL 필요**
- 요청서 표의 "낮음" 등급 대부분(1~8·14·15·20번: 지표·로그·이력 확인)이 이 단계로 해결된다
- 3장의 경보 시간차 개선을 같은 묶음에 넣는 것을 권장(같은 파일을 건드림)

**2차 — SMTP 테스트 연결 + 승인된 제한 조치** (규모: 중~대, 서버 상태를 바꾸는 첫 단계)

- 상세 페이지에서 시험 메일 실행(기존 기능 연결만)
- 사전 정의된 조치 ID 만 허용하는 조치 API 하나: 권한 재확인, 중복 실행 방지, 자동 만료 시각, 실행 전후 값 기록(감사 로그 재사용)
- 대상 조치 후보: 앱 단 IP 임시 차단·경로별 요청 제한(30단계 17번의 필터가 선행돼야 함), 범위가 정해진 캐시 키 초기화, 백업 상태 조회
- Cloudflare 규칙을 어드민에서 켜고 끄려면 Cloudflare API 토큰을 서버에 둬야 한다 → **외부 서비스 연동·자격증명 보관이라 별도 승인**
- 서버 명령 실행(재시작·백업 실행 등)은 WAS 가 셸을 실행하게 되는 구조라 이 단계에서 제외를 권장. 필요하면 별도 설계

**3차 — 보호 모드** (규모: 대, 신규 기능)

- 비핵심 기능 제한·조회 전용 모드·단계적 복구·자동 만료·운영진 승인·롤백
- 먼저 "비핵심 기능" 목록(통계·추천·업로드 등)과 자동 실행 범위를 클라이언트와 확정해야 착수 가능
- 요청서 표 18·19번, 30단계 20번이 여기에 해당

요청서의 "4차 장애 훈련"은 개발이 아니라 운영 확인이므로 테스트 서버(또는 7001 서버)가 생긴 뒤 진행한다.

## 3. 경보 메일과 복구 메일의 시간 차이 — 원인 분석

코드를 직접 다시 읽어 확인했다. 기본 설정값은 `AlertRules.java:82-101`(연속 확인 2회 :98, 연속 복구 2회 :99, 메일 최소 등급 위험 :84).

### ① 복구 조건이 "주의 기준 미만이 2회 연속"이다 — 가장 큰 원인

- 복구(RESOLVE)는 관측 등급이 **정상(NORMAL)** 일 때만 센다: `AlertStateMachine.java:142-161`.
- 열린 등급보다 낮은 비정상(예: 위험으로 열렸는데 지금은 주의)은 **경보를 그대로 유지**하고 아무 메일도 내지 않는다: `AlertStateMachine.java:191-195`. 등급을 낮추는 전이 자체가 없다(같은 파일 :15 주석 "낮아지는 건 그냥 유지").
- 정상 판정은 주의 임계값 미만이어야 한다: `AlertRules.java:109-123`.
- 예: RAM 기본값 주의 80·위험 90. 92%로 위험 경보가 열린 뒤 85%로 내려와도 경보는 열린 채이고, **80% 미만이 두 번 연속 나와야** 복구 메일이 나간다. 운영진이 보기에 "이미 괜찮아졌는데 복구 메일이 한참 뒤에 온다"가 여기서 생긴다.

### ② 5분 주기 × 연속 2회 — 열림·닫힘 각각 5~10분 지연

- 평가는 5분마다 한 번: `SystemAlertMonitor.java:113` (`0 2/5 * * * *`, 매시 2·7·12…분).
- 열 때 같은 등급 2회 연속 필요: `AlertStateMachine.java:165-189`. 실제 이상 시작부터 경보 메일까지 **5~10분**.
- 닫을 때 정상 2회 연속 필요: `AlertStateMachine.java:146-147`. 실제 정상화부터 복구 메일까지도 **5~10분**.
- 메일의 "발생 시각"은 실제 시작 시각이 아니라 **두 번째 관측 시각**이다: `AlertStateMachine.java:176-177`. 복구 메일의 "지속 시간"도 이 시각부터 센다(`SystemAlertMonitor.java:215-216`).
- 기본 메일 최소 등급이 위험이라(`AlertRules.java:84`), 주의로 먼저 열린 경보가 나중에 위험으로 오르면 "등급 상승" 메일이 처음 오는 메일이 되고(`SystemAlertMonitor.java:195-203`), 본문의 발생 시각은 그보다 앞선 주의 시점이다.

### ③ 로그인 실패는 15분 창으로 센다

- 집계 창 15분: `SystemAlertMonitor.java:51`, 사용 :540-541. 판정은 15분 합계가 기준(기본 20건) 이상이면 위험: `AlertRules.java:140-145`.
- 공격이 멈춰도 마지막 실패들이 15분 창에서 빠져나갈 때까지 계속 위험으로 관측된다. 그 뒤 정상 2회가 더 필요하므로 **공격 종료 후 최대 약 15~25분** 뒤에 복구 메일이 나간다.

### ④ 스케줄러가 스레드 하나를 모든 작업과 공유한다

- `context-common.xml:115` 의 `<task:annotation-driven />` 에 스케줄러(pool)를 지정하지 않았다. 이 경우 Spring 은 단일 스레드로 모든 `@Scheduled` 를 순서대로 돌린다(코드 주석도 이를 전제: `SystemAlertMonitor.java:112`).
- 같은 스레드를 쓰는 작업:
  - `DmExpireScheduler.java:24` — 매분
  - `PageGeneratorScheduler.java:125` — 10분마다(0·10·20…분), 6개국 × 최대 50페이지 생성
  - `SystemMetricsCollector.java:88` — 5분마다(0·5·10…분), `:98` 디렉터리 스캔 30분마다(3·33분), `:115` 자정 리셋
  - `StarDailyStatScheduler.java:27` — 매일 00:10
- 앞 작업이 길어지면 경보 평가(2·7·12…분)가 그만큼 늦게 시작한다. 특히 0·10·20…분의 페이지 생성 직후 2분 슬롯이 영향을 받기 쉽다. 실제 지연 폭은 운영 로그로 측정해야 한다.

### ⑤ 경보 메일이 3회 모두 실패하면 복구 메일이 아예 안 나간다

- 경보 메일은 최대 3회 시도(5초·15초 간격): `AlertMailService.java:43-44,118-141`.
- 성공했을 때만 `mailSent` 가 켜진다: `SystemAlertMonitor.java:243-246`. 실패하면 이벤트만 남긴다(:247-249).
- 복구 시 `mailSent` 가 꺼져 있으면 복구 메일을 보내지 않는다: `SystemAlertMonitor.java:214`.
- SMTP 가 잠깐 끊긴 사이 경보가 열리면 운영진은 경보 메일도, 복구 메일도 못 받는다. 경보 센터 이벤트 이력의 `MAIL_FAIL` 로 이 경우인지 확인할 수 있다.
- 메일 발송도 단일 스레드 큐다(`AlertMailService.java:58`). 메일 하나가 실패 재시도로 최대 약 50초(시도당 타임아웃 10초 × 3 + 대기 20초) 걸리므로, 여러 경보가 동시에 나면 뒤 메일이 그만큼 밀린다.

### ⑥ (추가 발견) DB 커넥션 풀 대기 무제한이 경보 전체를 멈출 수 있다

- `context-datasource.xml:41-44` 의 `maxActive`·`maxWait` 가 주석 처리돼 commons-dbcp 1.4 기본값(최대 8개, 대기 무제한)이 쓰인다.
- 경보 평가는 매번 DB 에서 설정을 읽고(`SystemAlertMonitor.java:132`) DB 상태를 잰다(:457 `getConnection`). 풀이 바닥나면 여기서 무기한 대기 → **스케줄러 스레드 하나가 묶여 경보·지표 수집·DM 만료가 모두 멈춘다**(④). DB 장애 때 경보가 늦거나 안 오는 원인이 될 수 있다.

### ⑦ (참고) "지금 점검" 버튼도 경보 집계에 들어간다

- 어드민의 "지금 점검"(`SuperAlertController.java:131` → `SystemAlertMonitor.java:123-126`)은 정기 평가와 같은 `evaluateOnce` 를 탄다. 버튼을 누르면 연속 횟수가 1회 늘어 경보가 5분 기다리지 않고 열리거나 닫힐 수 있고, 5xx 집계 구간도 짧아진다(:516-517). 운영진이 버튼을 누른 날과 안 누른 날의 시간차가 달라 보이는 이유가 될 수 있다.

### 개선안 — **승인 후 구현**

| 안 | 내용 | 비고 |
| --- | --- | --- |
| A. 즉시 가능한 설정 조정 | 어드민 경보 센터 설정에서 `alert.recover.count` 를 2 → 1 | 코드 변경 없음. 복구 지연 5분 단축. 오경보 플래핑이 늘 수 있음 |
| B. 히스테리시스 복구 | 열린 등급의 임계값보다 일정 폭(예: 5%p) 아래로 연속 내려오면 "등급 하향" 이벤트, 주의 미만이면 복구. 하향 시 메일 여부는 선택 | `AlertStateMachine` 수정 + 기존 테스트(`AlertStateMachineTest`) 보강 |
| C. 스케줄러 풀 | `context-common.xml` 에 스케줄러 pool(예: 3~4) 지정 | 설정 파일 수정. 각 스케줄러의 동시 실행 안전성 확인 필요(경보 평가는 이미 `synchronized`) |
| D. 메일 실패 정책 | 경보 메일 실패 기록이 있어도 복구 메일은 발송(본문에 "경보 메일 발송 실패 이력" 표기), 실패한 경보 메일은 다음 주기에 재시도 | `SystemAlertMonitor` 수정 |
| E. 로그인 실패 판정 | 15분 합계 대신 "최근 5분 신규 실패"로 복구 판정 | 판정 규칙 변경 |
| F. 발생 시각 표기 | 메일에 "최초 감지 시각"(첫 관측)과 "경보 확정 시각"을 함께 표기 | 상태 필드 1개 추가 |
| G. 커넥션 풀 값 지정 | `maxActive`·`maxWait` 지정(예: 대기 10초) | 설정 파일 수정. 11번과 같이 처리 |
| H. 수동 점검 분리 | "지금 점검"은 화면 갱신만 하고 연속 집계에는 넣지 않음 | 2장 1차와 같이 처리 권장 |

A 는 운영진이 바로 적용할 수 있다. 나머지는 2장 1차와 같은 파일을 건드리므로 1차 견적에 묶는 것을 권장한다.

## 4. 미결 질문 (클라이언트 회신 필요)

1. **숏폼 세로 확대 단위**: "라이브 세로 크기 1개분"이 정확히 무엇의 높이인지(로비 라이브 카드 1장 높이인지, 현재 숏폼 높이의 1배인지). Android "총 3개", iOS "총 2개"가 원래 높이 대비 배수인지, 지난번 확대 후 높이에 더하는 것인지 확인 필요. 화면 높이를 넘는 경우 상한도 정해야 한다.
2. **방문자 그래프 기준**: "앱을 켠 횟수"를 정확히 세려면 앱 실행 이벤트를 새로 보내고 저장 테이블을 만들어야 한다(**신규 이벤트 + DDL**, 그래프는 반영 이후 데이터부터 쌓임). 대안은 기존 `WH_STAR_DAILY_STAT` 를 국가(`PRS_COUNTRY`)별로 합산하는 방식(과거 데이터 즉시 표시 가능하나 "앱 실행 수"가 아니라 기존 방문 집계 기준). 어느 쪽인지, 그리고 "모든 유저"가 비로그인 웹 방문을 포함하는지 확인 필요.
3. **모바일웹 스타 프로필 클릭 시 "전체화면"의 의미**: (a) 로비처럼 콘텐츠를 세로 전체화면 피드로 넘겨 보는 화면을 여는 것인지, (b) 프로필의 동영상을 전체화면 플레이어로 바로 재생하는 것인지, (c) 프로필 페이지 자체를 헤더 없이 꽉 차게 보여주는 것인지. 메인 화면의 어느 요소(프로필 사진·이름·카드)를 누를 때인지도 필요.
4. **몽당연필 절반 크기 시 터치 영역**: 아이콘만 절반으로 줄이고 터치 영역은 현재 크기(최소 44pt 권장)로 유지할지, 터치 영역도 같이 줄일지. 줄이면 오터치·미터치가 늘 수 있어 아이콘만 줄이는 쪽을 권장한다.

추가로 1·2장 진행을 위해 필요한 것:

- 운영 서버 SSH(또는 운영 담당자가 대신 실행할 일정) — 30단계의 절반이 여기에 걸림
- Cloudflare 대시보드 접근 권한(04·16번)
- 외부 백업 보관소 선정·비용 승인(02번)
- 원클릭 2차의 Cloudflare API 연동 여부
