 1. 메일을 받았을 때 — 공통 절차 (5분 안에)
--------------------------------------------------------------------------------

  1단계  제목의 등급과 항목을 본다.
         [긴급] → 즉시 2절 긴급 절차. [위험] → 2절 위험 절차. [복구] → 3절.
  2단계  본문 링크 또는 어드민 > 경보 센터로 들어간다.
         - 열린 경보 목록에서 같은 경보 ID를 찾아 "확인"을 누른다.
           "확인"은 "담당자가 봤다"는 기록이다. 장애를 닫는 것이 아니다.
           확인하면 긴급 재알림이 멈추고 감사 이력에 누가 언제 확인했는지 남는다.
         - 서버 현황 블록에서 다른 항목도 같이 빨간지 본다. 경보는 혼자 오지 않는다
           (예: DB 긴급 + HTTP 5xx 위험이 같이 뜬다).
  3단계  어드민 > 시스템 관리에서 현재 수치를 본다. 메일은 발송 시점 값이고
         화면은 5초마다 갱신된 현재 값이다.
  4단계  운영 채널에 한 줄 공유: "경보 ID, 등급, 항목, 현재 수치, 확인자".
  5단계  등급에 따라 2절 조치. 운영자는 서버를 직접 조작하지 않는다. HQ에 알리고
         Incident를 등록한다.

  [Incident에 적을 것]
    경보 ID / 등급 / 항목 / 메일의 발생 시각 / 지금 수치 / 앱·웹 체감(안 열림·느림·
    특정 기능) / 직전 24시간 배포·설정 변경 여부 / 함께 뜬 다른 경보

 2. 등급·항목별 조치
--------------------------------------------------------------------------------

[긴급 — 즉시 HQ 전화/메신저 + Incident P1]
  디스크 95% 이상
    1) HQ에 즉시 통보. 배포·대용량 업로드·백업 작업을 중단시킨다.
    2) 어드민 > 시스템 관리 > 디렉터리 용량으로 어디가 큰지 적어 보낸다.
    3) HQ가 로그 로테이션·임시 파일 정리로 공간을 확보한다.
       사용자 콘텐츠·DB 파일·정산 로그는 삭제하지 않는다.
    4) 확보 뒤 앱 로그인·피드 업로드·어드민 대시보드가 되는지 확인한다.
  RAM 95% 이상
    1) HQ 즉시 통보. 2) 시스템 관리의 힙·GC·스레드 수치를 적어 보낸다.
    3) HQ가 상위 프로세스 확인 → 승인 절차 후 재시작. 4) 복원 뒤 10분 관찰.
  DB 연결 실패
    1) HQ 즉시 통보. 앱 전체(로그인·피드·랭킹)가 멈추는 장애다.
    2) 사용자 공지 필요 여부를 운영 책임자가 결정한다.
    3) HQ가 DB 프로세스·디스크·연결 수를 확인하고 복구한다. DB 재시작은 승인 후.
    4) 복구 메일을 받으면 3절 검증을 한다.

[위험 — HQ 메신저 + Incident P2, 30분 안에]
  디스크 85% 이상
    1) 디렉터리 용량 확인 → HQ에 "디스크 정리 요청". 2) 디스크 증가 추세의 소진
    예상일을 적는다. 3) 긴급으로 올라가면 위 절차.
  RAM 90% / CPU 90% 이상
    1) 시스템 관리에서 API 요청량·상위 경로를 본다. 특정 경로 폭주면 봇·남용 가능성.
    2) HQ에 알린다. HQ가 Cloudflare 요청 제한·비핵심 기능 제한 → 승인 후 재시작.
    3) 10분 이상 지속되는지 본다. 잠깐이면 "확인"만 하고 관찰.
  JVM 힙 95% 이상
    1) 시스템 관리 > "메모리 정리" 버튼 1회. 크게 내려오면 관찰, 안 내려오면 누수.
    2) GC 횟수·시간, 스레드 수를 적어 HQ에 알린다. 3) HQ가 힙 덤프·재시작 판단.
  Redis 연결 실패
    1) 앱은 DB로 대신 응답하므로 바로 멈추진 않는다. 느려지는지, DB 커넥션이
    차오르는지 본다. 2) HQ에 알린다. 설정은 건드리지 않는다. 3) 복구 메일 대기.
  HTTP 5xx 증가 (5분 20건·5% 이상)
    1) 같은 시각의 DB·Redis·힙 경보가 있는지 본다. 대개 원인은 그쪽이다.
    2) 시스템 관리 > 상위 경로로 특정 경로에 몰렸는지 본다.
    3) HQ에 알린다. 최근 배포가 있었으면 롤백 검토는 HQ.
  관리자 로그인 실패 15분 20건 이상
    1) 어드민 > 감사 로그에서 대상 계정·시각을 본다.
    2) 내 계정이면 비밀번호 즉시 변경 + OTP 상태 확인. 모르는 계정이면 보안사고
    절차(계정 보호 → 접근 제한 → 증적 보존 → HQ 통보).
    3) HQ가 Cloudflare에서 출처 차단.

[주의 — 메일은 오지 않는다 (화면 표시만)]
  경보 센터 서버 현황과 어드민 상단 띠에만 뜬다. 일일 점검 때 보고, 하루 넘게
  유지되면 HQ에 알린다.

 3. 복구(정상화) 메일을 받았을 때
--------------------------------------------------------------------------------

  1) 경보 센터에서 해당 경보가 닫혔는지, 열린 경보가 0건인지 본다.
  2) 실제 서비스를 사람이 확인한다(자동 복구는 수치만 본 것이다):
     - 앱: 로그인 → 로비 → 스타 페이지 → 게시물 1개 열기 → 댓글 1개
     - 공개 웹: 홈페이지, 스타 페이지 1개
     - 어드민: 대시보드, 시스템 관리 화면 수치 정상
  3) 운영 채널에 "경보 ID 복구, 지속 시간, 확인자" 한 줄.
  4) Incident를 "복구"로 바꾸고 복구 메일의 지속 시간·최고 등급을 적는다.
     원인 분석과 사후 보고서는 HQ가 작성하고 경보 ID를 첨부한다.
  5) 같은 항목이 하루에 두 번 이상 열리고 닫히기를 반복하면 임계값에 걸쳐 있는
     것이다. HQ와 임계값 조정 또는 근본 원인 처리를 상의한다.

 4. 수상한 경보 메일을 받았을 때 (위조·피싱 의심)
--------------------------------------------------------------------------------

  다음 중 하나면 링크를 누르지 않고 어드민에 직접 주소를 쳐서 들어가 확인한다.
  - 발신 주소가 witchhunting777@gmail.com 이 아니다(표시 이름만 같고 주소가 다름).
  - 본문에 비밀번호·OTP 입력·로그인 요구, 첨부 파일, 결제·송금 안내가 있다.
  - 경보 센터 이력에 같은 경보 ID가 없다.
  - 제목 형식이 0절과 다르다.
  위조로 판단되면 메일을 보관(삭제 금지)하고 HQ에 알린다. 발신 계정 비밀번호가

--------------------------------------------------------------------------------
 5. 메일을 보낸 뒤 — 발신 측 확인 (SM·HQ)
--------------------------------------------------------------------------------

[시험 메일을 보낸 뒤]
  어드민 > 경보 센터 > "시험 메일 발송" 을 누른 뒤:
  1) 경보 이력에 TEST_MAIL 행이 "성공"으로 남았는지 본다.
     실패면 같은 행에 오류 사유가 있다. 흔한 원인: 앱 비밀번호 틀림, 2단계 인증
     꺼짐, 포트 587 차단, 수신자 주소 미설정.
  2) "발송 성공"은 서버가 Gmail에 넘겼다는 뜻이다. 수신자 휴대전화에서 실제로
     받았는지 확인해야 완료다. 받은 메일함에 없으면 스팸함·프로모션 탭을 본다.
  3) 처음 받은 메일에서 발신인을 연락처에 추가하고 "스팸 아님" 처리한다.
  4) 수신자 전원이 받았는지 체크하고 결과를 기록한다(날짜, 수신자, 받은 시각).
  권장 주기: 월 1회. 수신자나 발신 계정을 바꾼 직후에는 반드시.

[실제 경보 메일이 나간 뒤]
  1) 경보 이력에 MAIL_SENT 가 남았는지 본다. MAIL_FAIL 이면 메일은 안 갔지만
     감시와 화면 표시는 계속된다 → 화면으로 대응하고, 메일 설정을 점검한다.
  2) 수신자가 1절대로 "확인"을 눌렀는지 본다. 긴급인데 60분 안에 확인이 없으면
     재알림이 나간다. 재알림 3회가 끝나도 확인이 없으면 전화로 직접 연락한다.
  3) 메일이 과하게 자주 오면(같은 항목이 하루 여러 번) 임계값·확인 횟수를 경보
     센터 설정에서 조정한다. 변경 전후 값은 감사 로그에 남는다.

[경보 메일이 계속 실패할 때 (MAIL_FAIL 반복)]
  1) 경보 센터 > 시험 메일로 재현한다.
  2) 발신 Gmail 계정에 로그인해 보안 경고(차단된 로그인 시도)가 있는지 본다.
     Gmail은 새 서버·새 지역에서의 SMTP 로그인을 막기도 한다. 경고에서 "본인 맞음"
     처리.
  3) 앱 비밀번호가 폐기됐는지 본다. 계정 비밀번호를 바꾸면 앱 비밀번호가 전부
     무효화된다. 이때는 새로 발급해 서버 설정에 다시 넣는다(HQ).
  4) 서버에서 587 포트 아웃바운드가 열려 있는지(HQ).
  5) 그동안 메일 없이 운영된 기간은 화면·외부 생존 감시로 대신 본다.

[발신 계정 관리 규칙]
  - witchhunting777@gmail.com 은 발신 전용 계정이다. 받은 메일함을 업무에 쓰지
    않고, 답장이 오면 운영자 메일로 전달 설정을 걸어 둔다.
  - 2단계 인증을 켠 상태를 유지한다(끄면 앱 비밀번호가 작동하지 않는다).
  - 앱 비밀번호 값은 서버 설정 파일에만 둔다. 메신저·문서에 적지 않는다.
  - 계정 복구 전화번호·이메일을 운영 책임자 것으로 등록해 둔다.
  - 이 계정으로는 경보·문의 알림·앱 발송 메일이 모두 나간다. 비밀번호를 바꾸면
    전부 멈추므로 변경은 HQ와 일정을 맞춘다.


--------------------------------------------------------------------------------
 6. 수신자 설정
--------------------------------------------------------------------------------

  어드민 > 경보 센터 > 설정 > 수신자. 쉼표로 여러 명.
  - 운영자 휴대전화 메일 1명 이상 + 운영 책임자 1명. HQ 담당자도 넣는 것을 권장.
  - 바꾼 뒤 반드시 시험 메일로 전원 수신 확인.
  - 퇴사·담당 변경 시 즉시 수정. 변경 이력은 감사 로그에 남는다.
  - 메일 최소 등급은 기본 "위험". "주의"까지 받고 싶으면 설정에서 낮출 수 있으나
    메일이 늘어난다.
