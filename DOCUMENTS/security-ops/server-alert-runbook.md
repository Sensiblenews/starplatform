# 서버 위험 경보 · 자동 이메일 알림 운영 매뉴얼 (2026-10-12)

어드민 **경보 센터**(`/super/alert/center.do`, SM 전용)와 5분 주기 감시기(`SystemAlertMonitor`)의 운영 안내다.
클라이언트 요청서 "서버 위험 경보·자동 알림 시스템 20단계"를 현 스택(Spring + 톰캣 + MariaDB + Redis, 기존 SMTP 빈 재사용)으로 구현했다.

---

## 1. 무엇을 감시하나

| 항목 | 측정 | 주의 | 위험 | 긴급 | 비고 |
|---|---|---|---|---|---|
| 디스크 | `monitor.disk.path`(기본 `/`) 사용률 | 75% | 85% | 95% | 요건 기본값. 설정에서 조정 |
| RAM | Linux `/proc/meminfo` MemAvailable 기준 (캐시는 여유로 봄) | 80% | 90% | 95% | 스왑 사용률은 설명에 표시 |
| CPU | 시스템 CPU 부하 | 80% | 90% | – | "지속"은 확인 횟수(2회=10분)로 구현 |
| JVM 힙 | 힙 used/max | 85% | 95% | – | 시스템 패널의 GC 지표와 함께 볼 것 |
| DB | `SELECT 1` (5초 타임아웃) | – | – | 연결 실패 | |
| Redis | PING | – | 연결 실패 | – | 앱은 캐시 실패 시 DB 폴백이라 위험까지만 |
| HTTP 5xx | 직전 5분 구간의 5xx 건수·비율 | – | 20건 이상 **그리고** 5% 이상 | – | 저트래픽 오경보 방지용 이중 조건 |
| 관리자 로그인 실패 | 최근 15분 비밀번호·OTP 실패 합계 | – | 20건 이상 | – | 계정 공격 징후 |

**감시하지 않는 것**: 톰캣 프로세스 자체의 다운. 감시기가 WAS 안에서 돌기 때문이다. 이것은 외부 생존 감시(3절)가 맡는다.
요청서의 "Node.js 프로세스"는 이 프로젝트에서는 톰캣(Java)이며, PM2 같은 프로세스 관리자는 쓰지 않는다.

## 2. 경보가 열리고 닫히는 규칙 (알림 피로도 방지)

- 같은 등급이 **확인 횟수(기본 2회 = 10분) 연속** 관측돼야 경보가 열린다. 잠깐 흔들리는 값은 경보가 되지 않는다.
- 항목당 열린 경보는 **하나**다. 같은 장애로 메일이 반복되지 않는다.
- 열린 뒤 **더 높은 등급**이 확인 횟수만큼 연속이면 "등급 상승" 메일 한 번. 낮아지는 건 그냥 유지.
- 정상이 **복구 횟수(기본 2회)** 연속이면 복구 처리. 메일이 나갔던 경보면 **복구 메일**(같은 경보 ID, 지속 시간, 복구 후 수치)을 보낸다.
- **주의(WARNING)** 는 화면 표시만, **위험(DANGER)** 이상부터 메일 (설정 `alert.mail.min.severity`).
- **긴급(CRITICAL)** 이고 아무도 "확인" 하지 않았으면 60분마다 최대 3회 재알림. "확인"은 복구와 별개다 — 담당자가 봤다는 표시일 뿐이다.
- WAS 를 재기동하면 DB 의 열린 경보를 복원하므로 같은 경보에 OPEN 메일이 다시 가지 않는다.

메일에 들어가는 것: 등급, 플랫폼 ID(`platform.id`, 기본 WITCH), 항목과 현재 수치, 발생 시각, 권장 조치, 경보 ID, 경보 센터 링크.
들어가지 않는 것: SMTP 인증정보, 비밀번호, 토큰.

## 3. 외부 생존 감시 (서버가 통째로 죽었을 때)

이 감시기는 서버가 살아 있을 때만 동작한다. 서버·네트워크 전체 장애는 **서버 밖**에서 봐야 한다.

1. 외부 업타임 서비스(예: UptimeRobot, Better Stack, Cloudflare Health Checks 등 승인된 것 하나)에 다음 URL 을 1~5분 간격으로 등록한다.
   - `https://witch-hunting.com/` (홈페이지, 200 기대)
   - `https://witch-hunting.com/api/super/lobby` 같은 공개 조회 API 1개 (JSON 200 기대)
2. 연속 2~3회 실패 시 운영자 이메일로 알리도록 설정한다.
3. **실제로 검증한다**: 점검 시간에 톰캣을 잠시 내리고 외부 알림이 실제로 오는지 확인한 뒤 올린다.
4. 외부 서비스 계정 정보는 비밀정보 규칙(47번)에 따라 보관한다.

이 항목은 서버·외부 계정 접근이 필요해 **개발 측에서 완료 처리하지 않았다** (NEEDS OPS).

## 4. 어드민 화면 사용법

- **서버 현황**: 항목별 현재 수치·등급. 열린 경보가 있으면 경보 번호와 "확인 처리" 링크.
- **지금 점검**: 다음 5분 주기를 기다리지 않고 1회 평가. (확인 횟수 규칙은 그대로 적용)
- **열린 경보 → 확인**: 담당자가 인지했음을 기록. 긴급 재알림이 멈춘다. 복구는 측정값이 정상으로 돌아와야 자동으로 된다.
- **설정 저장**: 수신자·임계값·피로도 파라미터. 변경 전후 값이 이력(SETTING_CHANGED)과 감사 로그(ALERT_SETTING_CHANGED)에 남는다.
- **시험 메일 발송**: 제목 `[TEST] StarPlatform 서버 알림 — 플랫폼 WITCH`. 결과는 이력(TEST_MAIL)에 남지만 **발송 성공 ≠ 수신 확인**이다. 운영자 휴대전화 메일 앱에서 실제 수신을 확인해야 완료다.
- 사이드바 **경보 센터** 배지에 열린 경보 수가 뜨고, 위험 이상이면 모든 어드민 화면 상단에 색 띠가 표시된다 (60초 폴링).

## 5. 장애·복구 시험 방법 (운영 데이터 훼손 없이)

| 시험 | 방법 | 기대 |
|---|---|---|
| 디스크 경보 | 설정에서 디스크 주의/위험 임계값을 현재 사용률보다 **낮게** 저장 → "지금 점검" 2회 | 경보 열림, 위험이면 메일 수신. 임계값 복원 후 2회 점검 → 복구 + 복구 메일 |
| CPU·RAM 경보 | 같은 방식으로 임계값을 현재값 아래로 | 동일 |
| DB 연결 실패 | 점검 시간에 DB 포트 방화벽을 잠시 막거나 DB 를 재시작(승인 필요) | 2회 연속 실패 뒤 긴급 경보 + 메일. 복구 뒤 복구 메일 |
| Redis 실패 | redis-server 를 잠시 중지 | 위험 경보. 앱 응답은 DB 폴백으로 계속되는지 함께 확인 |
| 홈페이지 접속 실패 | 외부 생존 감시(3절)로 검증 | 외부 서비스 알림 수신 |
| SMTP 실패 | SMTP 비밀번호를 틀리게 두거나 포트를 막고 시험 메일 | 이력에 MAIL_FAIL/TEST_MAIL 실패 기록, **감시 자체는 계속** |
| 재알림 | 긴급 경보를 확인하지 않고 60분 대기 (시험 시 `alert.remind.minutes` 를 5 로) | 재알림 메일 최대 3회 |

시험 후에는 임계값·재알림 설정을 기본값으로 되돌리고, 이력에서 시험 구간을 표시해 둔다.

## 6. 서버 설정 (globals.properties)

```
# 경보 메일 (수신자는 어드민 설정 테이블이 우선, 여기 값은 폴백)
alert.mail.from=            # 비우면 SMTP 계정 주소
alert.admin.url=            # 비우면 https://witch-hunting.com/super/alert/center.do
platform.id=WITCH           # 7001~7010 사본은 각 호기 ID
monitor.disk.path=/         # 감시할 파일시스템
```

SMTP 호스트·계정·비밀번호는 현재 `context-common.xml` 의 `mailSender` 빈에 있다. 이 파일은 Git 에 포함되므로
**설정 파일(globals.properties)로 이전 + 비밀번호 교체**가 필요하다 — 승인 항목으로 분리했다 (검토 문서 4절).

## 7. 7001~7010 호기 확대 적용

코드는 공통이고 호기별로 다른 것은 설정만이다.

1. 각 호기 DB 에 `db/sys-alert.sql`, `db/admin-mfa-audit.sql` 실행
2. 각 호기 `globals.properties` 에 `platform.id=7001` 등 호기 ID, 디스크 경로, (이전 후) SMTP 계정
3. 각 호기 어드민 경보 센터에서 **수신자**를 그 호기 운영사 주소로 저장하고 시험 메일 수신 확인
4. 외부 생존 감시에 호기 도메인 추가
5. 호기별 시험 결과(5절 표)와 미완료 항목을 기록해 제출

## 8. 긴급 상황별 첫 조치 (요건 매뉴얼 요약)

- **디스크 95%↑**: 배포·대용량 작업 중단 → `df -h`, `du -sh /var/lib/tomcat7/* /var/log/*` → 로그 로테이션·임시 파일 정리 → DB 파일·업로드 파일은 삭제 금지 → 확보 후 서비스·DB 확인
- **CPU·RAM 폭주**: `top` 상위 프로세스·최근 배포 확인 → Cloudflare Rate Limit → 비핵심 기능 제한 → 승인 후 재시작 → 단계적 복원
- **DB 손상·랜섬웨어 의심**: 접근 통제 → 백업 삭제 방지 → 증거 보존 → 깨끗한 환경에서 백업 복구 → 인증정보 교체 후 재개 승인
- **관리자 OTP 분실**: `otp-operator-guide.md` 3절
