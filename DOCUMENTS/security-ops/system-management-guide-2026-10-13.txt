 StarPlatform (WITCH) 시스템 관리 — 체크 방법과 조치 방법 종합 설명문
 요청서 31~46항 기준 / 작성일 2026-10-13 / 대상: 총운영사 시스템 관리자(SM 권한)
================================================================================

이 문서는 어드민 "시스템 관리" 화면과 "경보 센터" 화면에 실제로 있는 항목을
기준으로, 운영자가 무엇을 보고(체크 방법), 어떤 값이면 정상이고, 아니면 무엇을
해야 하는지(조치 방법)를 항목별로 적은 것이다.

요청서 47항(비밀번호 / Secret)은 비밀정보 위치와 조치 목록이 들어가므로
이 문서에 넣지 않고 별도 보안 채널로 따로 전달한다.


--------------------------------------------------------------------------------
 0. 먼저 알아둘 것
--------------------------------------------------------------------------------

[화면 위치]
  - 시스템 관리 : 어드민 사이드바 > 시스템 관리. SM(슈퍼 관리자) 계정만 열린다.
                  LC(지역 관리자)는 대시보드로 되돌려 보낸다.
  - 경보 센터   : 어드민 사이드바 > 경보 센터. SM 전용. 등급별 현황, 열린 경보,
                  이메일 수신자·임계값 설정, 경보 이력.
  - 감사 로그   : 어드민 사이드바 > 감사 로그. 관리자 로그인·OTP·설정 변경 기록.

[갱신 주기]
  - 시스템 관리 화면의 순간값(힙, CPU, 디스크, Redis, DB, 스레드 등)은
    5초마다 자동 갱신된다. 새로고침할 필요 없다.
  - "비용 지표(구간값)" 블록(트래픽, 디스크 추세, API 요청량, 상위 경로)은
    서버가 5분마다 수집한 표본으로 계산한다. 서버를 재시작하면 이 이력은 사라지고
    "수집 시작 이후"부터 다시 쌓인다. (24시간치 보관)
  - 디렉터리 용량은 30분마다 한 번만 스캔한다.
  - 경보 센터의 감시기는 5분마다 판정한다. "지금 점검" 버튼으로 즉시 1회 평가할 수
    있다.

[색 규칙 — 시스템 관리 화면]
  막대그래프 색은 다음 기준으로 바뀐다. 노랑은 "주의해서 보기", 빨강은 "조치".
    JVM Heap        : 60% 이상 노랑, 80% 이상 빨강
    CPU             : 60% 이상 노랑, 80% 이상 빨강 (서버 설정으로 조정 가능)
    디스크           : 70% 이상 노랑, 85% 이상 빨강 (서버 설정으로 조정 가능)
    톰캣 처리 스레드  : 60% 이상 노랑, 80% 이상 빨강
    파일 디스크립터   : 60% 이상 노랑, 80% 이상 빨강
    Redis / DB      : 초록 점 = 정상(UP), 빨간 점 = 중단(DOWN)

[경보 센터 기본 임계값 — 메일이 나가는 기준]
  경보 센터는 시스템 관리 화면과 별도로 아래 기준으로 등급을 매기고, "위험" 이상이면
  이메일을 보낸다. 값은 경보 센터 > 설정에서 바꿀 수 있다.
    항목          주의     위험     긴급
    디스크 사용률  75%      85%      95%
    RAM 사용률    80%      90%      95%
    CPU 사용률    80%      90%      -
    JVM 힙        85%      95%      -
    DB 연결       -        -        연결 실패
    Redis 연결    -        연결 실패 -
    HTTP 5xx      -        5분간 20건 이상 그리고 전체의 5% 이상
    관리자 로그인 실패 -    15분간 20건 이상
  같은 등급이 2회 연속(10분) 관측돼야 경보가 열리고, 정상이 2회 연속이면 자동 복구된다.
  긴급 경보를 아무도 "확인"하지 않으면 60분마다 최대 3회 다시 알린다.

[운영자가 할 수 있는 것 / 없는 것]
  어드민 화면에서 서버 상태를 바꾸는 기능은 "메모리 정리(GC)" 버튼 하나뿐이다.
  재시작, 설정 변경, DB·Redis 조작, 파일 삭제는 어드민에 없으며 HQ/기술지원 작업이다.
  운영자의 역할은 "보고, 분류하고, 알리는 것"이다.

 31. System Management — 화면 구성
--------------------------------------------------------------------------------

시스템 관리 화면은 위에서 아래로 다음 블록으로 되어 있다.

  (1) JVM 블록
      - JVM Heap Memory 실시간 현황 (사용 MB / 최대 MB / 사용률 막대)
      - 메모리 최적화 도구 ("메모리 정리" 버튼)
      - JVM Active Threads (현재 / 최고 / 데몬)
      - JVM Non-Heap Memory
      - JVM & System Info (자바 버전, OS, 가동 시간, 시작 시각, 로드 평균)
  (2) 시스템 리소스 & 연동 상태
      - CPU 사용률 (시스템 전체 / 이 프로세스)
      - 디스크 사용량 (Total / Used / Free)
      - Redis (UP/DOWN, 메모리, peak, 클라이언트 수, 키 수, 축출된 키)
      - Database (UP/DOWN, 활성 커넥션 / 유휴 / 최대)
      - Queue : "N/A — 메시지 큐 미도입". 이 시스템에는 작업 큐가 없다.
  (3) 비용 지표 (구간값)
      - 아웃바운드 트래픽 (최근 5분 / 1시간 / 24시간 / 당일 / 월 예상, 앱 응답 비중)
      - 디스크 증가 추세 (GB/시간, 소진 예상일)
      - API 요청량 (5분 / 1시간 / 당일, 분당 요청, 2xx·3xx·4xx·5xx 분포)
      - 응답 바이트 상위 경로 (경로별 요청 수 / 응답 MB, 상위 10개)
  (4) 런타임 상세
      - 디렉터리 용량 (업로드 / 로그 / 임시 — 서버 설정에 경로를 넣어야 표시)
      - 가비지 컬렉션 (총 횟수, 총 소요 시간, 가동시간 대비 %)
      - 톰캣 (처리 스레드 사용률, 활성 세션)
      - 파일 디스크립터 (열린 수 / 상한, 사용률)

요청서 항목과의 대응:
  JVM / Heap / Active Threads / Non-Heap / JVM 정보 ...... (1)
  System CPU / Disk ..................................... (2)
  Redis / Database ...................................... (2)
  Queue ................................................. (2) 해당 없음 표시
  Outbound Traffic / Disk Trend / API Request / Response Route ... (3)
  Directory Size / Garbage Collection / Thread Pool ..... (4)


--------------------------------------------------------------------------------
 32. 시스템 모니터링 원칙
--------------------------------------------------------------------------------

총운영사는 시스템 상태를 확인하고 보고한다. Core Infrastructure는 바꾸지 않는다.

[운영자가 보는 것]            [어디서]
  정상 / 비정상                 시스템 관리 상단 색, 경보 센터 서버 현황
  장애 여부                     경보 센터 열린 경보, 어드민 상단 색 띠
  Disk 증가                     시스템 관리 > 디스크 사용량, 디스크 증가 추세
  CPU 이상                      시스템 관리 > CPU 사용률
  DB 이상                       시스템 관리 > Database
  Redis 이상                    시스템 관리 > Redis
  API 오류                      시스템 관리 > API 요청량 (5xx 배지)
  Queue 적체                    해당 없음 (큐 미도입)
  Traffic 급증                  시스템 관리 > 아웃바운드 트래픽

[HQ가 담당하는 것]
  Core Server, DB 구조, Redis 구조, API Core, 보안·WAF(Cloudflare), 인프라,
  배포, 코어 패치. 운영자는 이 영역의 이상을 발견하면 Incident를 등록하고 기다린다.

[일상 점검 루틴 — 권장]
  매일 1회
    - 경보 센터: 열린 경보가 있는가. 있으면 "확인" 누르고 담당자에게 알린다.
    - 시스템 관리: 빨강 막대가 있는가. 디스크 Free가 줄고 있는가.
    - API 요청량: 5xx 배지가 0에 가까운가.
  매주 1회
    - 디스크 증가 추세의 "소진 예상일"이 30일 이내인가.
    - 응답 바이트 상위 경로에 낯선 경로가 올라와 있는가.
    - 감사 로그: 모르는 관리자 로그인·설정 변경이 있는가.
  매월 1회
    - 경보 센터 > 시험 메일 발송으로 운영자 휴대전화에 실제 수신되는지 확인.
    - 관리자 계정 목록 점검(46항).

 33. JVM Memory
--------------------------------------------------------------------------------

[체크 방법]
  시스템 관리 > JVM Heap Memory 실시간 현황.
  "사용 MB / 최대 MB"와 사용률 막대를 본다. 몇 분 지켜보면서 올라갔다 내려오는지,
  계속 오르기만 하는지 본다. 같은 화면의 가비지 컬렉션(42항)과 Active Threads를
  함께 본다.

[정상]
  - 사용률이 오르내린다. GC 뒤에 바닥값이 내려온다.
  - 막대가 초록(60% 미만)이거나 잠깐 노랑이었다가 돌아온다.
  - CPU 정상, 앱·웹 응답 정상.

[경고]
  - 사용률이 계속 오르고 GC 뒤에도 바닥이 높아진다.
  - GC 총 횟수·총 소요 시간이 빨리 늘어난다. 가동시간 대비 GC %가 수 %를 넘는다.
  - Active Threads 현재값이 계속 는다.
  - 경보 센터에 "JVM 힙 주의(85%)"가 뜬다.

[장애]
  - 경보 센터 "JVM 힙 위험(95%)" + HTTP 5xx 경보가 같이 뜬다.
  - 앱·웹이 느려지거나 응답하지 않는다. 서버 로그에 OutOfMemoryError.
  - 톰캣이 반복 재시작된다.

[조치]
  1. 경고 단계: "메모리 정리" 버튼을 한 번 누른다. 이 버튼은 JVM에 GC를 요청하고
     해제된 MB를 보여준다. 누른 뒤 사용률이 크게 내려오고 다시 서서히 오르면
     정상 범위의 누적이다. 거의 안 내려오면 누수 가능성이므로 아래로 간다.
  2. 시각, 사용률, GC 횟수·시간, 스레드 수를 적어 HQ에 Incident를 등록한다(P2).
     힙 덤프·원인 분석은 HQ가 한다.
  3. 최근 배포·설정 변경이 있었는지 HQ에 확인한다.
  4. 장애 단계: 승인 후 톰캣 재시작(HQ). 재시작 뒤 시스템 관리에서 힙이 낮은 값에서
     시작해 안정되는지 10분 이상 본다.

[주의]
  - "메모리 정리" 버튼은 해결책이 아니라 진단 도구다. 자주 누르면 오히려 응답이
    잠깐 멈춘다. 하루 여러 번 눌러야 할 상황이면 Incident 대상이다.


--------------------------------------------------------------------------------
 34. Disk Management
--------------------------------------------------------------------------------

[체크 방법]
  시스템 관리 > 디스크 사용량에서 Total / Used / Free와 사용률 막대를 본다.
  시스템 관리 > 디스크 증가 추세에서 "GB/시간"과 "소진 예상일"을 본다.
  시스템 관리 > 디렉터리 용량에서 업로드 / 로그 / 임시 중 어디가 큰지 본다.

[정상]
  - 사용률 70% 미만(초록). 소진 예상일이 30일보다 멀다.
  - 증가 속도가 평소 수준이다(평소값을 한 번 적어두면 비교가 쉽다).

[경고]
  - 70~85%(노랑) 또는 경보 센터 "디스크 주의(75%)".
  - 소진 예상일이 30일 이내로 들어온다.
  - 특정 디렉터리가 갑자기 커졌다.

[장애]
  - 85% 이상(빨강) / 경보 센터 "디스크 위험(85%)" / "긴급(95%)".
  - 95%를 넘으면 업로드 실패, 로그 기록 실패, DB 쓰기 실패가 연쇄로 난다.

[조치]
  1. 어디가 큰지 먼저 확인한다: 디렉터리 용량 카드. 이 시스템에서 가장 큰 증가
     요인은 업로드 영상이다. 로그 폭주 문제는 2026-09에 수정됐다.
  2. 경고 단계: HQ에 "디스크 정리 요청" Incident 등록(P3). 수치와 디렉터리를 적는다.
  3. 긴급 단계(95%): 즉시 HQ 통보(P1). 배포·대용량 업로드·백업 작업을 중단시킨다.
     HQ가 로그 로테이션·임시 파일 정리로 공간을 확보한 뒤 서비스·DB를 확인한다.
  4. 운영자가 서버 파일을 직접 지우지 않는다(35항).

[감시 대상 디렉터리]
  업로드(이미지·영상), 로그(톰캣 catalina, 애플리케이션 로그), 임시 파일, 백업,
  캐시. 디렉터리 용량 카드에 "감시 대상 디렉터리가 설정되지 않았습니다"가 보이면
  서버 설정에 경로가 안 들어간 것이므로 HQ에 설정을 요청한다.


--------------------------------------------------------------------------------
 35. Disk Guard
--------------------------------------------------------------------------------

디스크가 100%에 도달하는 것을 막는다.

[자동 정리 — 서버 쪽에서 처리]
  어드민에는 자동 삭제 기능이 없다. 오래된 톰캣 로그·임시 파일·캐시·오래된
  모니터링/내보내기 파일은 서버의 로그 로테이션(HQ 관리)으로 정리한다.
  어드민에 삭제 버튼을 두지 않은 이유: 사용자 콘텐츠와 보존 의무 자료를 실수로
  지우는 경로를 만들지 않기 위해서다.

[절대 삭제하지 않는 것]
  - 사용자 콘텐츠: 업로드 이미지·영상·썸네일
  - 거래·정산 자료: 광고 노출 로그 등 정산 근거 테이블
  - 법률상 보존 자료: 약관 동의, 신고·제재 이력, 감사 로그
  - DB 데이터 파일

[운영자 체크]
  - 디스크 증가 추세의 소진 예상일을 주 1회 본다.
  - 로그 디렉터리가 업로드 디렉터리보다 커지면 로그 폭주 가능성이므로 HQ에 알린다.


--------------------------------------------------------------------------------
 36. Redis
--------------------------------------------------------------------------------

[체크 방법]
  시스템 관리 > Redis 카드. 점 색과 "정상(UP) / 중단(DOWN)" 글자. 아래에 메모리,
  peak, 클라이언트 수, 키 수, 축출된 키가 보인다.

[정상]
  - 초록 UP. 축출된 키(evicted)가 0 또는 늘지 않음. 메모리가 peak 근처에서
    머무르며 급증하지 않음.

[경고]
  - 축출된 키가 계속 는다(메모리 부족 — 캐시가 밀려나고 있음).
  - 클라이언트 수가 평소의 몇 배로 는다.

[장애]
  - 빨간 DOWN. 경보 센터 "Redis 위험(연결 실패)".
  - 이 시스템은 Redis가 죽어도 앱이 DB로 대신 응답하도록 되어 있다(캐시 폴백).
    그래서 서비스가 바로 멈추지는 않지만 응답이 느려지고 DB 부하가 오른다.
    같은 시점의 CPU·DB 커넥션·5xx를 함께 본다.

[조치]
  1. 운영자는 Redis 설정을 바꾸지 않는다.
  2. DOWN이면 HQ에 Incident 등록(P2). 시각, 직전 메모리·클라이언트·축출 수치,
     앱 체감 상태를 적는다.
  3. 복구되면 경보 센터가 자동으로 복구 처리하고 복구 메일을 보낸다. 복구 뒤
     축출된 키가 다시 0부터 시작하는지 확인한다.

[미구현]
  - 적중률(Hit/Miss)은 화면에 없다. 필요하면 추가 과제.


--------------------------------------------------------------------------------
 37. Database
--------------------------------------------------------------------------------

[체크 방법]
  시스템 관리 > Database 카드. 점 색과 UP/DOWN, 활성 커넥션 / 유휴 / 최대.
  경보 센터 서버 현황의 DB 항목(5초 안에 간단 조회가 성공하는지로 판정).

[정상]
  - 초록 UP. 활성 커넥션이 최대의 절반 아래에서 오르내린다.

[경고]
  - 활성 커넥션이 최대에 붙어 있고 유휴가 0 — 느린 쿼리나 잠금으로 커넥션이
    돌아오지 않는 상태. 이때 보통 응답이 느려지고 5xx가 늘기 시작한다.

[장애]
  - 빨간 DOWN. 경보 센터 "DB 긴급(연결 실패)". 로그인·피드·랭킹 전부 실패.

[조치]
  1. 운영자는 DB를 직접 수정하지 않는다. 데이터 정정·테이블 변경·OTP 우회 목적의
     DB 조작 모두 금지.
  2. 경고: HQ에 Incident 등록(P2). 커넥션 수치와 시작 시각, 당시 상위 경로를 적는다.
  3. 장애: 즉시 HQ 통보(P1). 복구 뒤 앱 로그인·피드·어드민 대시보드가 열리는지
     확인한다.

[미구현 — 어드민에 없는 것]
  Slow Query, Lock, Storage, Replication은 DB 서버 쪽에서 봐야 한다(단일 DB,
  복제 없음). 필요 시 HQ가 DB 서버에서 확인한다.


--------------------------------------------------------------------------------
 38. API Monitoring
--------------------------------------------------------------------------------

[체크 방법]
  시스템 관리 > API 요청량: 최근 5분 / 1시간 / 당일 요청 수, 분당 요청, 상태코드
  배지(2xx 초록 / 3xx / 4xx 노랑 / 5xx 빨강).
  시스템 관리 > 응답 바이트 상위 경로: 어떤 경로가 요청·응답량을 많이 쓰는지 10개.

[핵심 경로]
  /post/{id}, /star/{id}  ... 공개 웹 페이지
  /api/...                ... 앱 API
  /super/...              ... 어드민
  /video/..., /img/...    ... 업로드 파일 전송

[정상]
  - 5xx 배지가 0이거나 극소수. 4xx는 어느 정도 있는 게 정상(잘못된 요청, 봇).
  - 상위 경로가 평소와 비슷한 순서.

[경고]
  - 5xx가 늘기 시작. 특정 경로가 갑자기 상위로 올라옴.
  - 요청 수가 평소의 몇 배 — 봇·크롤링·남용 가능성.

[장애]
  - 경보 센터 "HTTP 5xx 위험"(5분간 20건 이상이면서 5% 이상).

[조치]
  1. 5xx 경보가 뜨면 경보 센터에서 "확인"을 누르고, 같은 시각의 DB·Redis·힙 경보가
     있는지 본다. 대개 원인은 그쪽이다.
  2. HQ에 Incident 등록. 5xx 수치, 상위 경로, 시작 시각을 적는다.
  3. 요청 폭주가 특정 경로·특정 출처에서 오면 HQ가 Cloudflare에서 차단·속도 제한을
     건다. 운영자는 Cloudflare 설정을 직접 바꾸지 않는다.

[미구현]
  - 응답 시간(latency) 분포는 화면에 없다.


--------------------------------------------------------------------------------
 39. HTTP Status 관리
--------------------------------------------------------------------------------

  2xx  정상 처리.
  3xx  리다이렉트. 로그인 이동 등 정상 동작에 포함된다.
  4xx  사용자 요청 문제: 없는 주소(404), 권한 없음(401/403), 잘못된 입력(400).
       사용자 실수·봇 탐색이 대부분. 갑자기 몇 배로 늘면 스캔·공격 징후.
  5xx  서버 오류. 코드 오류, DB·Redis 연결 실패, 메모리 부족.

[조치 기준]
  - 5xx가 갑자기 늘면 Incident를 만든다. 경보 센터가 자동으로 "위험" 경보를 열고
    메일을 보내지만, 저트래픽 시간대에는 20건 기준에 못 미쳐 경보 없이 5xx가 쌓일
    수 있다. 그래서 일일 점검 때 5xx 배지를 눈으로 본다.
  - 4xx 급증은 경보 대상이 아니다. 상위 경로와 감사 로그(관리자 로그인 실패)를
    함께 보고 공격 징후면 HQ에 알린다.


--------------------------------------------------------------------------------
 40. Outbound Traffic
--------------------------------------------------------------------------------

[체크 방법]
  시스템 관리 > 아웃바운드 트래픽: 최근 5분 MB, 1시간 GB, 24시간 GB, 당일 GB,
  월 예상 GB, 그리고 "앱 응답 비중"(전체 송신 중 애플리케이션 응답이 차지하는 %).
  아래 작은 차트로 5분 단위 추이를 본다.

[정상]
  - 월 예상 GB가 서버 요금제 한도 안이다. 앱 응답 비중이 평소와 비슷하다.

[경고 — 급증 시 확인 순서]
  1. 상위 경로에 /video/ 가 올라왔는가 → 영상 다운로드·재생 증가. 정상일 수도 있다
     (인기 게시물). 동시에 요청 수가 비정상적으로 많으면 봇.
  2. /img/ 가 올라왔는가 → 이미지. 썸네일 대량 조회.
  3. 요청 수는 적은데 바이트가 많다 → 대용량 파일 반복 다운로드.
  4. 요청 수가 많고 경로가 다양하다 → 크롤링·스캔.
  5. 앱 응답 비중이 급락했다 → 애플리케이션 밖(정적 파일, 다른 프로세스)에서
     송신이 늘었다는 뜻. HQ 확인 필요.

[조치]
  - 급증이 1시간 이상 지속되면 HQ에 알린다. 수치(1시간 GB, 상위 경로)를 첨부한다.
  - 봇·크롤링·공격이면 HQ가 Cloudflare에서 차단한다.

[미구현·제약]
  - 트래픽 임계값 경보는 없다. 서버 요금제의 과금 방식(월 한도·초과 요금)이
    확정되면 임계값을 정해 추가한다.
  - 서버를 재시작하면 당일·누적 수치가 0부터 다시 시작한다.


--------------------------------------------------------------------------------
 41. Directory Monitoring
--------------------------------------------------------------------------------

[체크 방법]
  시스템 관리 > 디렉터리 용량. 업로드 / 로그 / 임시 각각 GB, 파일 수, 마지막 스캔
  시각. 30분마다만 갱신된다.

[읽는 법]
  - "truncated" 표시가 있으면 파일이 너무 많아 스캔을 중간에 끊은 것이다.
    표시된 값은 실제보다 작다. 이 경우 실제 크기는 HQ가 서버에서 확인한다.
  - "감시 대상 디렉터리가 설정되지 않았습니다"가 보이면 서버 설정 누락. HQ에 요청.

[정상]
  - 업로드가 가장 크고 천천히 는다. 로그·임시는 작고 일정하다.

[경고]
  - 로그가 하루 사이 수 GB 늘었다 → 로그 폭주. HQ에 알린다.
  - 임시 디렉터리가 계속 는다 → 변환 실패 잔여물 가능성. HQ에 알린다.

[확장]
  - 백업·모니터링 디렉터리도 서버 설정에 키를 추가하면 같은 카드에 표시된다.


--------------------------------------------------------------------------------
 42. Garbage Collection
--------------------------------------------------------------------------------

[체크 방법]
  시스템 관리 > 가비지 컬렉션: 총 실행 횟수, 총 소요 시간, 가동시간 대비 %.
  아래 줄에 컬렉터별(Young / Old) 횟수·시간이 보인다.

[정상]
  - 가동시간 대비 GC %가 1~2% 이하. Old(Full) GC 횟수가 하루에 몇 번 수준.

[경고]
  - GC %가 5%를 넘어 계속 오른다. Old GC가 몇 분마다 돈다.
  - 힙 사용률이 GC 뒤에도 안 내려온다(33항 경고와 동일).

[조치]
  - 33항 JVM Memory 조치 순서를 따른다. GC 수치는 Incident에 꼭 적는다.
  - 톰캣 카드의 "처리 스레드" 사용률과 "파일 디스크립터"도 함께 본다.
    파일 디스크립터가 꾸준히 늘기만 하면 커넥션·파일 누수 신호라 재시작으로
    잠깐 해결돼도 반드시 HQ 분석 대상이다.


--------------------------------------------------------------------------------
 43. 서버 장애 대응 — Incident Process
--------------------------------------------------------------------------------

  Detection      경보 센터 메일·어드민 상단 색 띠·외부 생존 감시·사용자 신고
       ↓
  Classification 44항 등급표로 P1~P4 결정
       ↓
  Notification   운영 채널에 공유. P1·P2는 HQ에 즉시 전화/메신저 + Incident 등록
       ↓
  Containment    HQ: Cloudflare 속도 제한·차단, 문제 기능 임시 제한
       ↓
  Diagnosis      HQ: 서버 로그·시스템 관리 수치·경보 이력으로 원인 파악
       ↓
  Recovery       HQ: 재시작·롤백·설정 복구
       ↓
  Verification   운영자: 앱 로그인·피드·랭킹·어드민 대시보드·공개 웹 확인
       ↓
  Root Cause     HQ 작성
       ↓
  Post-Incident  경보 ID, 이력, 시간대별 수치 첨부해 보고서 제출
  Report

[Incident 등록 시 적을 것]
  - 발견 시각, 발견 경로(메일 / 화면 / 신고)
  - 등급(P1~P4)
  - 경보 센터 경보 ID(있으면)
  - 시스템 관리 수치: 힙 %, CPU %, 디스크 %, Redis/DB 상태, 5xx 수, 상위 경로
  - 사용자 체감(앱이 안 열림 / 느림 / 특정 기능만 실패)
  - 직전 24시간 내 배포·설정 변경 여부

[외부 생존 감시]
  경보 센터의 감시기는 서버 안에서 돌기 때문에 서버 자체가 죽으면 알림을 못 보낸다.
  그래서 외부 업타임 서비스에 홈페이지 URL과 공개 API URL 하나를 등록해 두어야 한다.
  이 설정은 서버·외부 계정 작업이라 HQ와 함께 완료 여부를 확인한다.


--------------------------------------------------------------------------------
 44. 장애 등급
--------------------------------------------------------------------------------

  등급        정의             예                              경보 센터 대응
  P1 Critical 전체 서비스 장애  App/Web Down, DB 연결 실패       긴급(CRITICAL), 재알림
  P2 Major    핵심 기능 장애    로그인/랭킹 실패, Redis 다운+지연 위험(DANGER)
  P3 Normal   일부 기능 장애    특정 메뉴, 5xx 소폭 증가          주의/위험
  P4 Minor    경미한 문제       UI/텍스트                        경보 아님

  실제 Response / Recovery 시간은 Annex 6 및 Commercial Order Form의 SLA를 따른다.


--------------------------------------------------------------------------------
 45. 보안사고
--------------------------------------------------------------------------------

[징후 — 어디서 보나]
  - 경보 센터 "관리자 로그인 실패(15분 20건)" 경보
  - 감사 로그에 모르는 시간·모르는 계정의 로그인, OTP 실패 반복, 설정 변경
  - API 요청량의 4xx 급증, 상위 경로에 /super/login 등 어드민 경로
  - 사용자 신고(계정 탈취, 이상 게시물)

[즉시 조치 순서]
  1. 이상행위 확인 — 감사 로그에서 계정·시각·행위를 적는다.
  2. 계정 보호 — 해당 관리자 계정 비밀번호 변경, OTP 재설정, 필요 시 계정 비활성.
  3. 접근 제한 — HQ가 Cloudflare에서 출처 차단·어드민 경로 접근 제한.
  4. 증적 보존 — 서버 로그, 감사 로그, 경보 이력을 복사해 둔다(HQ). 지우지 않는다.
  5. HQ 통보 — Incident 등록(보안 분류).
  6. 추가 확산 차단 — 같은 비밀번호를 쓰는 다른 계정·서비스 점검, 비밀정보 교체(47항).

  개인정보 침해가 의심되면 Annex 4의 Incident Response를 적용한다.


--------------------------------------------------------------------------------
 46. Admin 보안
--------------------------------------------------------------------------------

모든 관리자에게 적용:
  - 강력한 비밀번호: 길고(12자 이상) 다른 서비스와 다르게.
  - MFA: 어드민 Google OTP 이중인증이 적용되어 있다. SM·LC 모두 의무. 첫 로그인 때
    등록 화면이 뜬다. 분실 시 절차는 OTP 운영 안내문을 따른다.
  - 개별 계정: 사람마다 계정 하나. 공용 계정 금지.
  - 계정 공유 금지: 비밀번호·OTP 화면을 타인에게 보여주지 않는다.
  - 최소권한: 전체 권한(SM)은 꼭 필요한 사람만. 지역 운영은 LC.
  - 정기 권한 검토: 월 1회 관리자 목록과 감사 로그를 보고 불필요한 계정을 정리한다.
  - 퇴사자 즉시 권한 회수: 계정 비활성 + OTP 재설정. 공유된 비밀정보가 있으면 교체.
  - API Secret 공유 금지: 서버 비밀정보는 운영자에게 전달되지 않는다. 받았다면 47항
    규칙으로 처리한다.


--------------------------------------------------------------------------------
 47. 비밀번호 / Secret
--------------------------------------------------------------------------------

원칙만 적는다. 실제 비밀정보의 위치·현황·조치 목록은 별도 보안 채널 문서로
전달하며 이 문서에는 넣지 않는다.

  다음 정보를 메신저·이메일·문서·스크린샷에 평문으로 공유하지 않는다.
    DB Password, SSH Key, API Secret, OAuth Secret, Cloud Credential,
    Payment Credential, Encryption Key
  전달이 꼭 필요하면 비밀번호 관리 도구 공유 기능이나 암호화 파일 + 별도 경로 비밀번호를
  쓴다. 전달 후 가능한 한 빨리 교체한다.
