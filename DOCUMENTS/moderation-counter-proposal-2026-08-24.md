# 콘텐츠 관리 방안 역제안 — 사전 승인 대신 신고 체계 고도화

2026-08-24

## 요약

이미지 검열 요청의 목적에는 전적으로 동의합니다. 다만 제안 주신 **"AI 판정 전까지 이미지를 비공개로 묶는 사전 승인 방식"**은 SNS 서비스에서 쓰이지 않는 구조이며, 사용자 이탈과 운영 부담이라는 큰 비용을 치르고도 정작 목표를 충분히 달성하지 못합니다.

대신 **현행 신고 제도를 체계화하는 방향**을 제안드립니다. 지금 StarPlatform의 신고 기능은 절반이 이메일로 새고 있고, 자동 조치가 하나도 없으며, 처리 이력이 남지 않습니다. 이 셋만 해결해도 유해 콘텐츠 노출 시간이 "관리자가 발견할 때까지"에서 "신고 몇 건 누적되는 순간"으로 줄어듭니다. 사전 승인 없이도 말입니다.

---

## 1. 먼저 정확히 해둘 것

논의의 정확도를 위해 한 가지를 분명히 하겠습니다.

**주요 SNS도 업로드 시점에 자동 검사를 합니다.** Meta·TikTok 등은 업로드되는 이미지에 대해 해시 매칭과 머신러닝 분류를 돌립니다. 아동 성착취물(CSAM) 해시 매칭은 법적 의무 영역이기도 합니다.

**다만 어느 곳도 "판정이 끝날 때까지 공개를 막지" 않습니다.** 콘텐츠는 즉시 공개되고, 탐지와 조치는 비동기로 따라갑니다. 문제가 발견되면 그때 내립니다.

즉 쟁점은 "AI를 쓰느냐 마느냐"가 아니라 **"AI 판정을 공개 게이트로 삼느냐"**입니다. 전자는 업계 표준이고, 후자는 표준이 아닙니다. 이번 제안서의 핵심 원칙인 *"APPROVED가 아니면 URL을 주지 않는다"*가 바로 후자에 해당합니다.

## 2. 사전 승인 방식이 SNS에서 쓰이지 않는 이유

**① 즉시성이 무너집니다.** 사용자가 사진을 올리고 "검토 중입니다"를 보는 순간, 그것은 SNS가 아니라 게시판 승인 대기열입니다. 친구에게 "지금 올렸어"라고 말할 수 없는 서비스는 SNS로 기능하지 않습니다.

**② 운영 부담이 업로드량에 정비례합니다.** 사전 승인은 업로드되는 **모든** 콘텐츠를 검토 대상으로 만듭니다. 신고 기반은 문제가 제기된 것만 봅니다. 업로드가 늘수록 전자는 선형으로 무거워지고, 후자는 그렇지 않습니다.

**③ 판정 주체가 없습니다.** 현재 StarPlatform에는 AI 검열 연동이 전혀 없습니다(코드 확인 완료). 사전 승인을 도입하면 판정은 사람이 하게 되고, 그 사람이 볼 때까지 사용자의 사진은 계속 "검토 중"입니다. 새벽에 올린 사진은 아침까지 안 보입니다.

**④ 사용자 반발.** "내 사진이 심사 대기 중"이라는 경험은 이용자 입장에서 검열로 받아들여집니다.

## 3. 스토어 정책이 실제로 요구하는 것

앱스토어·구글플레이의 UGC 정책이 요구하는 것은 **사전 승인이 아닙니다.**

| 요구 항목 | 현재 상태 | 역제안 후 |
|---|---|---|
| 유해 콘텐츠 필터링 수단 | 부분 (신고만, 자동 조치 없음) | 자동 임계 조치 + 사유별 우선순위 |
| 신고 수단 | 절반만 (댓글만 앱 내, 게시물은 이메일) | 전 대상 앱 내 신고 |
| 신고에 대한 적시 대응 | **증명 불가** (이력 없음) | 처리 이력 + 대응 시간 지표 |
| 악용 사용자 차단 | 있음 (기기 차단) | 단계별 제재로 확장 |
| 연락처 공개 | 있음 | 유지 |

지금 가장 취약한 칸은 **"적시 대응"**입니다. 대응했다는 기록 자체가 남지 않기 때문에, 심사나 분쟁 상황에서 증명할 자료가 없습니다. 사전 승인을 만드는 것보다 이쪽을 메우는 것이 실질적입니다.

## 4. 현행 신고 제도 실측

코드를 전수 확인한 결과입니다.

| 신고 대상 | 신고 수단 | DB 기록 | 어드민 노출 | 자동 조치 |
|---|---|---|---|---|
| 댓글 | 앱 내 신고 (사유 3종) | O | O | **없음** |
| 게시물 · 스타 페이지 | **이메일(mailto:)** | **X** | **X** | **X** |
| 이미지 | **없음** | X | X | X |
| 사용자 개인 차단 | 앱 내 차단 | O | X | — |

### 구조적 결함 8가지

1. **신고가 두 갈래로 새고 있습니다.** 게시물·스타 신고는 사용자의 메일 앱을 열어 개인 지메일로 보냅니다. 기록·집계·추적이 전부 없고, 메일 앱이 없는 기기에서는 아예 동작하지 않습니다.
2. **이미지 신고 경로가 없습니다.** 정작 리스크가 가장 큰 대상입니다.
3. **중복 신고를 막지 않습니다.** 한 사람이 같은 대상을 몇 번이든 신고할 수 있어, 신고 건수를 판단 근거로 쓸 수 없습니다.
4. **자동 조치가 전혀 없습니다.** 신고가 몇 건 쌓이든 관리자가 화면을 열기 전까지 유해 콘텐츠는 그대로 노출됩니다.
5. **처리 이력이 없습니다.** 누가 언제 무엇을 했는지 남지 않아 대응 시간을 증명할 수 없습니다.
6. **조치 수단이 2개뿐입니다.** 댓글 삭제 / 영구 차단. 중간 단계가 없어 과잉 아니면 과소 대응만 가능합니다.
7. **신고자에게 결과를 알리지 않습니다.** 신고해도 달라진 게 없어 보이면 다시 신고하지 않게 됩니다.
8. **허위 신고자에 대한 제재가 없습니다.**

## 5. 역제안 — 신고 체계 고도화 7단계

### 1단계. 신고 창구 일원화
이메일 신고를 없애고 모든 신고를 앱 내 폼으로 받아 DB에 기록합니다. 신고 대상을 **댓글 / 게시물 / 이미지 / 프로필**로 확장합니다.
> 기존 신고 테이블이 이미 "대상 종류 + 대상 ID" 구조라, 스키마를 크게 바꾸지 않고 확장할 수 있습니다.

### 2단계. 신고 사유 표준화
현재 3종(부적절/욕설/광고)을 정책·법규 기준에 맞춰 넓힙니다 — 성적 콘텐츠 / 폭력·혐오 / 괴롭힘 / 스팸·광고 / 저작권 / 사칭 / 기타. **사유별로 임계값과 우선순위를 다르게** 둡니다. 성적 콘텐츠는 1건만 들어와도 검토 큐 최상단으로 올립니다.

### 3단계. 중복 신고 차단
같은 기기가 같은 대상을 중복 신고하지 못하게 막습니다. 이것이 없으면 신고 건수를 신뢰할 수 없어 4단계가 성립하지 않습니다.

### 4단계. 자동 임계 조치 — **이 제안의 핵심**
유효 신고가 기준 건수에 도달하면 **관리자 개입 없이 즉시 비공개 처리**합니다.

```
유해 콘텐츠 게시
      ↓
사용자 신고 누적 (사유별 2~3건)
      ↓
자동 블라인드 — 관리자 대기 없음
      ↓
관리자가 확인 후 복구 또는 확정
```

이것이 *"관리자가 볼 때까지 노출된다"*는 문제의 실질적 해법입니다. 사전 승인 없이도 노출 시간을 **분 단위**로 줄일 수 있습니다. 삭제가 아니라 블라인드이므로 오탐이어도 복구됩니다.

### 5단계. 제재 단계화
현재의 "댓글 삭제 / 영구 차단" 사이를 채웁니다 — **경고 → 게시 제한(24시간·7일) → 영구 차단**. 위반 누적 횟수를 기준으로 자동 승급합니다.

### 6단계. 처리 이력 + 운영 지표
모든 자동·수동 조치에 처리자·시각·사유·조치 내용을 남깁니다. 어드민 메인에 **미처리 건수 / 최장 대기 시간 / 24시간 내 처리율**을 노출합니다. 스토어 심사와 분쟁 대응에서 "우리는 이렇게 대응했다"를 증명하는 자료가 됩니다.

### 7단계. 신고자 피드백 + 악용 방지
처리 결과를 신고자에게 알립니다. 허위 신고가 반복되는 기기는 신고 가중치를 낮춰 4단계 자동 조치가 악용되지 않게 합니다.

## 6. 두 방식 비교

| | 사전 승인 (원안) | 신고 체계 고도화 (역제안) |
|---|---|---|
| 업로드 → 공개 | 관리자 승인까지 대기 (수 시간) | 즉시 |
| 유해 콘텐츠 노출 시간 | 0 (승인 전 비공개) | 신고 누적까지 (분~시간) |
| 검토 대상 | 업로드되는 **전부** | 신고된 것만 |
| 운영 부담 | 업로드량에 정비례 | 신고량에 비례 |
| 외부 AI 계약 | 필요 (업체·비용 미정) | 불필요 |
| 적용 범위 | 이미지만 | 이미지·게시물·댓글·프로필 전부 |
| 사용자 경험 | 심사 대기 | 기존과 동일 |

### 정직하게 말씀드릴 한 가지

역제안 방식은 **최초 노출을 막지 못합니다.** 누군가 신고하기 전까지는 보입니다. 이 점을 감추지 않겠습니다.

그 대신 얻는 것이 즉시성이고, 이것이 주요 SNS가 모두 선택한 트레이드오프입니다. 만약 그 최초 노출조차 허용할 수 없다는 판단이시라면 사전 승인 외에 방법이 없으며, 그때는 공개 지연과 상시 검토 인력이라는 비용을 함께 받아들이셔야 합니다. 그 경우의 설계는 이미 정리해 두었으니 말씀 주시면 그대로 진행하겠습니다.

## 7. 공수

| 단계 | 추정 |
|---|---|
| 1. 신고 창구 일원화 (이메일 제거, 대상 확장) | 1.5일 |
| 2. 신고 사유 표준화 | 0.5일 |
| 3. 중복 신고 차단 | 0.5일 |
| 4. 자동 임계 조치 | 1일 |
| 5. 제재 단계화 | 1.5일 |
| 6. 처리 이력 + 운영 지표 | 1.5일 |
| 7. 신고자 피드백 + 악용 방지 | 1일 |
| 테스트·배포 검증 | 1일 |
| **합계** | **8.5일** |

**1~4단계만 먼저(4~5일)** 진행해도 핵심 효과 — 신고 누락 방지와 자동 차단 — 는 확보됩니다. 5~7단계는 운영 성숙도를 올리는 단계라 이어서 진행해도 무방합니다.

## 8. 확인이 필요한 항목

1. **자동 블라인드 임계값** — 사유별 몇 건으로 할지 (제안: 성적 콘텐츠 2건, 그 외 3건)
2. **제재 단계 기준** — 몇 회 위반에서 게시 제한, 몇 회에서 영구 차단인지
3. **대응 목표 시간(SLA)** — 신고 접수 후 몇 시간 내 처리를 목표로 할지. 이 값이 정해져야 운영 지표를 만들 수 있습니다
4. **DB 스키마 변경 승인** — 신고 테이블 제약 추가, 처리 이력 테이블 신설
5. **신고 결과 통지 수단** — 푸시 / 앱 내 알림 / 미통지
