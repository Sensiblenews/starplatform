# 서버 경보 원클릭 대응 — 사용 방법 및 완료 체크리스트 (2026-10-21)

## 1. 사용 방법

### 1-1. 경보가 오면 (메일 → 클릭 → 조치)

1. **경보 메일을 받는다.** 등급이 "위험" 이상일 때 발송됩니다. "주의"는 메일 없이 경보 센터 화면에만 표시됩니다.
   - 제목 형식: `[위험] StarPlatform <플랫폼> — <항목> 발생`
   - 본문 내용: 현재 수치, 발생 시각, 경보 번호, 권장 조치, **"▶ 이 경보 확인·조치"** 링크
2. **메일의 링크를 누른다.**
   - 로그인과 OTP를 거치면 대시보드가 아니라 **그 경보의 상세 화면**이 바로 열립니다.
   - 이미 로그인된 상태라면 상세 화면이 바로 열립니다.
3. **상세 화면에서 상황을 확인한다.**
   - **지금 상태**: 마지막 측정값과 등급
   - **최근 24시간 그래프**: 해당 항목이 언제부터 올랐는지 보여 줍니다. 주의·위험·긴급 기준선이 함께 그려집니다.
   - **권장 조치 순서**: 항목별로 무엇부터 확인할지 단계별로 보여 줍니다.
   - **경과**: 발생 → 메일 → 확인 → 조치 → 복구 기록
4. **원클릭 조치 버튼을 쓴다.** (표 1-2 참고)
5. **한 일을 "조치 메모"로 남긴다.**
   - 예: "로그 정리 요청함", "서버 담당자에게 재시작 요청"
   - 누가 언제 무엇을 했는지가 경과와 감사 로그에 남습니다.
6. **수치가 내려가면 경보가 저절로 복구되고 복구 메일이 온다.**
   - 복구 메일에도 상세 화면 링크가 있습니다.

### 1-2. 원클릭 조치 버튼

| 버튼 | 하는 일 | 서버 영향 |
|---|---|---|
| 이 항목 다시 측정 | 그 항목만 지금 다시 읽어서 결과를 바로 보여 줍니다. | 없음. 조회만 하며 경보를 열거나 닫지 않습니다. |
| 확인 처리 | "담당자가 보고 있음" 표시를 남깁니다. 긴급 경보의 재알림 메일이 멈춥니다. | 없음 |
| 메모리 정리 (GC) | JVM 메모리를 한 번 정리합니다. JVM 힙·RAM 경보에서만 보입니다. | 아주 잠깐 응답이 느려질 수 있습니다. |
| 경보 메일 시험 발송 | 설정된 수신자에게 시험 메일을 보냅니다. | 없음 |
| 조치 메모 | 한 일을 기록합니다(최대 500자). | 없음 |

**이 화면에서 하지 않는 조치**: 서버 재시작, DB 재시작, IP 차단·Cloudflare 규칙 변경, 백업 실행·복원, 보호 모드.
이런 조치는 잘못 누르면 서비스 전체에 영향을 줍니다. 그래서 서버 담당자가 직접 하고, 운영진은 요청한 내용을 조치 메모로 남깁니다.

### 1-3. 경보 센터 (평소 점검)

- 위치: 어드민 → 경보 센터 (`/super/alert/center.do`, 총괄관리자 SM 전용)
- **서버 현황**: 디스크·RAM·CPU·JVM 힙·DB·Redis·HTTP 5xx·관리자 로그인 실패를 5분마다 측정합니다. "지금 점검" 버튼을 누르면 바로 측정합니다.
- **열린 경보**: 행마다 **[상세·조치]** 버튼이 있습니다. 경보 번호를 눌러도 상세 화면으로 갑니다.
- **경보·메일 설정**: 수신자, 임계값, 메일을 보낼 최소 등급, 확인·복구 횟수를 바꿀 수 있습니다. 변경 내용은 감사 로그에 남습니다.

### 1-4. 경보가 열리고 닫히는 규칙

| 구분 | 규칙 |
|---|---|
| 열림 | 같은 등급이 **2회 연속**(5분 간격, 약 10분 지속) 측정되면 열립니다. |
| 등급 상승 | 더 높은 등급이 2회 연속이면 메일을 한 번 다시 보냅니다. |
| 복구 | 열린 등급보다 **낮은 값**이 2회 연속이면 복구됩니다.<br>예: "위험"으로 열린 디스크 경보가 "주의" 수준으로 내려오면 위험 경보는 복구 메일과 함께 닫힙니다. 이후 주의 수준이 계속되면 주의 경보가 화면에만 새로 열립니다. |
| 재알림 | 긴급 경보를 아무도 확인 처리하지 않으면 60분마다 최대 3회 다시 보냅니다. |

## 2. 배포 후 확인 체크리스트

**배포 준비** (개발 측)

- [ ] 서버 WAR 배포. 이번 변경은 모두 서버 쪽이고 DB 변경(DDL)은 없습니다.
- [ ] 배포 후 서버 로그에 스케줄러·DB 풀 관련 오류가 없는지 확인

**기능 확인** (운영진 + 개발 측)

- [ ] 경보 센터 → 설정에서 수신자 이메일 확인 → **시험 메일 발송** → 휴대전화 메일 앱에서 실제로 받았는지 확인
- [ ] 경보 센터 → 열린 경보(또는 최근 경보)의 **[상세·조치]** → 상세 화면이 열리는지
- [ ] 상세 화면 → **이 항목 다시 측정** → 결과가 바로 바뀌고, 경과에 `ACTION` 기록이 남는지
- [ ] 상세 화면 → **조치 메모** 저장 → 경과에 남는지
- [ ] 로그아웃 → 메일 링크 형태 주소(`/super/alert/detail.do?id=경보번호`)를 연다 → 로그인·OTP 후 **그 상세 화면**으로 들어가는지
- [ ] 다음에 실제 경보 메일이 왔을 때 링크가 상세 화면으로 열리는지
- [ ] 복구 메일이 예전보다 빨리 오는지. 주의 수준으로 내려와도 복구로 처리되어야 합니다.

**설정 확인** (서버 담당자)

- [ ] 서버 설정 `alert.admin.url`을 따로 넣어 두었다면, 값이 `https://<도메인>/super/alert/center.do` 형식인지 확인
  - 이 형식이면 메일 링크가 자동으로 상세 주소로 바뀝니다.
  - 다른 주소라면 `?alertId=` 파라미터가 붙고, 경보 센터가 이를 받아 상세 화면으로 넘깁니다.

## 3. 요청 항목별 처리 현황

판정 기준:

| 표기 | 뜻 |
|---|---|
| ✅ **완료** | 코드가 있고 바로 쓸 수 있습니다. |
| 🛠 **이번에 개선** | 2026-10-21 이번 작업으로 새로 넣거나 고쳤습니다. |
| 🔑 **서버/외부 권한 필요** | 개발이 아니라 서버·Cloudflare·외부 계정을 가진 담당자가 설정하고 증빙해야 합니다. |
| ⏸ **보류(권장 안 함)** | 현재 규모에서는 얻는 것보다 위험·비용이 커서 하지 않기로 한 항목입니다. |

### 3-1. 원클릭 운영센터 (요청 2번)

| 요청 | 현황 |
|---|---|
| 경보 메일 → 클릭 한 번으로 해당 경보 화면 | 🛠 이번에 개선 (상세 링크, 로그인·OTP 후 복귀) |
| 경보별 현재 상태·원인·영향·권장 조치 표시 | 🛠 이번에 개선 (지금 상태, 24시간 그래프, 권장 조치 단계) |
| 최신 상태 재확인 | 🛠 이번에 개선 (항목별 다시 측정, 조회 전용) |
| 담당자 확인·조치 이력 기록 | ✅ 확인 처리 + 🛠 조치 메모, 경과, 감사 로그 |

| 범위가 제한된 조치(메모리 정리) | 🛠 이번에 개선 (JVM 힙·RAM 경보에서만) |
| 승인된 요청 제한·IP 임시 차단 | 🔑 Cloudflare 규칙으로 처리 (앱에서 제어하려면 API 토큰 보관 등 별도 승인 필요) |

### 요약

- **개발로 할 수 있는 핵심은 끝났습니다.** 메일 → 클릭 → 상세 확인 → 안전한 조치 → 기록 → 복구 메일까지 이어집니다. 경보·복구 메일 시간차도 개선했고, DB 연결이 무한정 대기하던 위험도 없앴습니다.
- **나머지 상당수(🔑)는 개발이 아니라 서버·Cloudflare 담당자의 설정 작업입니다.** 위 표의 🔑 항목을 담당자 체크리스트로 쓰면 됩니다.
- **⏸ 항목은 지금 규모에서는 권장하지 않습니다.** 트래픽이 크게 늘거나 7002~7010을 운영할 때 다시 검토합니다.
